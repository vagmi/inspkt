# inspkt — Roadmap

> Generated by /onboard, re-planned 2026-06-14 for the richer domain model.
> Check off phases as they ship. Each phase is a vertical slice and ends
> deployable. Product scope: `prds/base.md` (note: the data model below
> supersedes the flat "items" model in the original PRD).

## What we're building
A multi-tenant inspection platform. An organization (the inspection company)
sets up reusable **forms**, onboards **clients** and their **facilities**,
registers the **equipment** at each facility, and assigns **inspectors** to
perform inspections. Every submitted inspection is automatically scored into an
explainable verdict (pass / conditional / fail) with corrective actions and
re-inspection scheduling.

**Data model:** `Client → Facility → Equipment (of an Equipment Type)`.
A **Form** is the rubric for an Equipment Type. An **Inspection** targets a
piece of Equipment + a Form, is performed by an assigned Inspector, and produces
**observations**, a **verdict**, and **corrections / re-inspections**.

**Roles (Clerk):** **Admin/Owner** (sets up the instance), **Manager**
(oversees, assigns work, follows up), **Inspector** (performs assigned
inspections). The app has an **admin/manager mode** (setup + oversight) and an
**inspector mode** (my assigned inspections).

**UI:** Tailwind v4 + shadcn/ui, plus **react-hook-form + zod** for forms and
**TanStack Table** for data grids (`app/components/ui/form.tsx`,
`data-table.tsx`). All MIT-licensed; no second design system.

**Billing:** paid plans via Polar (free tier with limits, paid unlock).

## Shipped so far (v1 — flat model)
Phases 0–3 shipped the working spine against a flat **items** model (no clients/
equipment, single role). Phases 7 and 9 evolve that spine into the hierarchy
above — `items` becomes `facilities`, and inspections retarget from item →
equipment. Nothing is thrown away; it's migrated.

## Phases

### [x] Phase 0 — Environment setup
Clerk (Organizations enabled) + D1 + local migrations green. App renamed
mudhal → inspkt. **Shipped.**

### [x] Phase 1 — Inspectable registry (`items`)
`items` table with category + geo-location, full CRUD slice. **Shipped.**
→ Evolves into **Facilities** in Phase 7.

### [x] Phase 2 — Inspection form builder
`forms` + `checkpoints` (four answer types, severity, critical flag,
photo-required, sectioned + ordered); builder UI. **Shipped.**
→ Forms attach to an **Equipment Type** in Phase 8.

### [x] Phase 3 — Inspection capture (with photos)
`inspections` + `observations`, draft/resume/submit, geo-tagging, photo upload
to a **private** R2 bucket served via authenticated `/api/uploads/:key`.
**Shipped** (see security note at the bottom). → Retargets item → **equipment**
in Phase 9.

### [x] Phase 4 — UI toolkit foundation
**Goal:** an enterprise forms + tables foundation, one design system.
**Shipped (2026-06-14):** added `react-hook-form`, `@hookform/resolvers`,
`@tanstack/react-table`; created `app/components/ui/form.tsx` (RHF + zod) and
`data-table.tsx` (sortable/filterable/paginated grid over shadcn Table).
**Convention going forward:** every new entity screen uses `<Form>` +
`zodResolver` for create/edit and `<DataTable>` for lists. Existing hand-coded
screens (items, forms, capture) migrate opportunistically, not in a big-bang.

### [ ] Phase 5 — Roles & access modes
**Goal:** Admin / Manager / Inspector roles, and an app that shows the right
mode to each.
**Prereq (you):** in the Clerk dashboard, add the custom org roles
`org:manager` and `org:inspector` (org:admin exists). 
**Slice:** expand `app/lib/capabilities.ts` with `can.setup` (admin),
`can.assign` / `can.manage` (admin+manager), `can.inspect` (all) — gate on the
Clerk **session** role, never the membership mirror → enforce with
`requireCapability` on every setup/assign route → role-aware nav + a
role-aware `/app` landing (admin/manager → setup dashboard; inspector → "my
inspections"). 
**Done when:** an inspector signing in sees only inspector mode; an admin sees
setup; capabilities unit-tested; deploys.

### [ ] Phase 6 — Clients
**Goal:** admins/managers onboard the customers the org inspects for.
**Slice:** `clients` table (org-scoped: name, contact, notes) → clients-repo →
clients-service (plan gate later) → clients-controller (zod) → routes:
`clients-list.tsx` (**DataTable**) + create/edit (**RHF Form**), admin/manager
gated. Mirror tests at every layer.
**Done when:** create a client, see it in a sortable/searchable table, edit it;
deploys.

### [ ] Phase 7 — Facilities (evolve `items`)
**Goal:** facilities belong to a client; today's items become facilities.
**Slice:** rename `items` → `facilities`; add `client_id` FK (+ index); keep
geo-location. Migration renames the table/columns and backfills a default
client for any existing rows. Update repo/service/controller/route names and
the capture references. Facility list is a **DataTable** scoped by client;
create/edit is an **RHF Form** with a client picker + map location.
**Done when:** facilities list under their client; existing inspections still
resolve; tests green; deploys.

### [ ] Phase 8 — Equipment + Equipment Types
**Goal:** register the actual inspectable assets, typed, and link forms to types.
**Slice:** `equipment_types` (org-scoped taxonomy; **a Form attaches to a
type** — add `form_id`/`type_id` link) + `equipment` (`facility_id`, `type_id`,
identifier, optional own geo) → repos/services/controllers → routes: equipment
list per facility (**DataTable**) + create/edit (**RHF Form** with facility +
type pickers); a small Types admin screen.
**Done when:** add a type with its form, add equipment of that type to a
facility; deploys.

### [ ] Phase 9 — Retarget inspections to Equipment
**Goal:** inspections are performed against equipment, not bare items.
**Slice:** add `equipment_id` to `inspections` (migrate `item_id` →
`equipment_id`; the form is derived/validated from the equipment's type) →
update inspections-repo/service joins (equipment → facility → client names) →
capture "new inspection" picks **equipment** (scoped by client/facility) and
auto-selects the type's form. Location mismatch now compares against the
equipment's (or facility's) registered location.
**Done when:** start an inspection by choosing equipment; capture + submit work
as before; tests green; deploys.

### [ ] Phase 10 — Assignments & inspector queue
**Goal:** managers assign work; inspectors execute it.
**Slice:** `assignments` (equipment_id, form_id, inspector_user_id, due_at,
status open/done) → repo/service (creating an assignment seeds a draft
inspection owned by the inspector) → controller (manager/admin gated for create;
inspector reads own) → manager UI to assign (**RHF Form**: inspector + equipment
+ form + due date) and an inspector "My assignments" queue (**DataTable**) that
launches capture.
**Done when:** a manager assigns an inspection to an inspector; the inspector
sees and performs it; deploys.

### [ ] Phase 11 — Verdict engine + follow-up
**Goal:** every submitted inspection yields an explainable verdict. Core of the
product.
**Slice:** `corrections` + verdict fields on `inspections` (score 0–100,
verdict `pass|conditional|fail`, `reinspection_due_at`) → pure **verdict-service**
(per-checkpoint resolve → pass/warn/fail; critical override; severity-weighted
score; tiers; corrections for conditional; re-inspection date for fail) → wired
into `submit` → capture shows the verdict + why.
**Done when:** a failed critical checkpoint forces Fail + re-inspection date
regardless of score; minor-only ⇒ Conditional + corrections; exhaustively
unit-tested; deploys.

### [ ] Phase 12 — Inspection report
**Goal:** a structured, print-friendly report per inspection.
**Slice:** service-level assembly (inspection + equipment + facility + client +
form + observations + photos + verdict + corrections) → `GET
/inspections/:id/report` → `inspection-report.tsx` with verdict badge,
section-by-section results, photos in context, corrections + re-inspection date;
print stylesheet.
**Done when:** open any submitted inspection → full report renders and prints.

### [ ] Phase 13 — Role-aware dashboard
**Goal:** close the loop — nothing overdue gets lost; each role sees its view.
**Slice:** lifecycle status (`… → reinspection_scheduled → closed`) + repo
queries → dashboard-service → role-aware `/app` landing: **manager/admin** see
open work, recent verdicts, **overdue re-inspections/corrections**, equipment by
latest verdict; **inspector** sees their queue + due dates. Actions to close
corrections and start a due re-inspection.
**Done when:** overdue items surface without searching; closing corrections
moves an inspection to closed; deploys.

### [ ] Phase 14 — Billing via Polar
**Goal:** paid plans gate the operation.
**Slice:** `pnpm install-skill billing-polar` → define plans in `getPlan()`
(e.g. free = N clients / facilities / equipment / inspections-per-month; paid =
unlimited) → enforce in the relevant services via `getPlan().max*` +
`usageRepo.increment`; upgrade CTA when a gate trips.
**Done when:** a free org hitting a limit gets an upgrade prompt; checkout lifts
the gate; deploys.

### [ ] Phase 15 — Production hardening
**Goal:** inspkt production-ready on Cloudflare.
**Build:** switch Clerk to a **production instance** (with the custom roles
configured there too), all secrets via `wrangler secret put`, remote migrations,
production webhook URLs (Clerk org-sync, Polar), `pnpm deploy`; smoke-test the
full journey across all three roles.
**Done when:** admin sets up a client/facility/equipment → manager assigns →
inspector inspects → verdict + report → dashboard, all on the production URL.

---

### Security note — R2 bucket is PRIVATE (from Phase 3)
The `r2-uploads` skill defaults to a public bucket + unguessable keys; that was
rejected for sensitive inspection photos. `inspkt-uploads` has public access
**disabled**; photos are served only through the authenticated
`GET /api/uploads/:key` route (Clerk session + org-prefix check). Keep this
private-read pattern for any sensitive content.
